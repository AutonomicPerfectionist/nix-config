# Agent Guidelines for This NixOS Configuration Repository

This is a NixOS flake-based system configuration repository. It manages multiple hosts, users, and reusable modules.

## Build Commands

### Evaluating the configuration
```bash
# Evaluate the entire flake (checks for errors)
nix eval .#nixosConfigurations.hypergamma.config.system.build.toplevel

# Evaluate a specific host configuration
nix flake show . --show-trace
```

### Building and applying configurations
```bash
# Apply configuration to a specific host (from a running NixOS system)
sudo nixos-rebuild switch --flake .#hostname

# Example hosts: hypergamma, goblin, aj-framework, lucy, big-nix,
#                thunder-budget-3, thunder-budget-4, arid-wind,
#                fatman-3, king-blue, queen-blue

# Dry-run to see what would change
sudo nixos-rebuild dry-build --flake .#hostname

# Build VM for testing
nix build .#nixosConfigurations.hostname.pkgs.system
```

### Update workflow
```bash
# Run the update script: ./update.sh <hostname> [-f]
# -f flag also updates flake inputs (nix flake update)

./update.sh hypergamma      # Just rebuild
./update.sh hypergamma -f  # Update flakes then rebuild
```

## Linting

### Nix formatting
```bash
# Format all Nix files (uses nixfmt-rfc-style)
nix fmt

# Format specific file
nixfmt-rfc-style path/to/file.nix

# Format in place
nixfmt-rfc-style --write path/to/file.nix
```

### Nix language server (nil)

```bash
# Configure in your editor to use 'nil' as the LSP
# Works with VS Code, Neovim, etc.

```

### Nix validation tools
```bash
# Check for unused imports (deadnix)
deadnix .

# Check for syntax errors
nix-instantiate --parse path/to/file.nix

# Validate the flake
nix flake check

# Full evaluation check
nix eval .#nixosConfigurations.hypergamma.config.system.build.toplevel
```

## Code Style Guidelines

### File Structure
- Each Nix file should be an attribute set with the standard signature:
  ```nix
  {
    config,
    lib,
    pkgs,
    flake-inputs,  # for Home Manager user configs
    userConfiguration,  # for user modules
    ...
  }:
  {
    # configuration goes here
  }
  ```

### Indentation and Formatting
- Use **2 spaces** for indentation (observed in existing files)
- Align attributes within attribute sets
- Use multi-line lists when they have more than 2-3 items:
  ```nix
  environment.systemPackages = with pkgs; [
    vim
    git
    wget
  ];
  ```

### Imports
- Use relative paths for local imports: `./module.nix` or `../../modules/foo.nix`
- Group imports logically at the top of the file
- Separate groups with blank lines

### Naming Conventions
- **Host names**: kebab-case (e.g., `hypergamma`, `aj-framework`)
- **Module names**: kebab-case (e.g., `nix-settings.nix`, `hyprland.nix`)
- **User names**: lowercase (e.g., `b`, `branden`, `aj`)
- **Option names**: camelCase for NixOS options, kebab-case for CLI tools

### Package References
- Always use `with pkgs;` when referencing multiple packages
- For single packages, inline is fine: `pkgs.vim`

### Option Usage
- Use `lib.mkEnableOption` for boolean options
- Use `lib.mkIf` for conditional configuration blocks
- Use `lib.mkOption` with type definitions for custom options
- Always provide descriptions for custom options

### Error Handling
- Nix will fail fast on type errors - no runtime error handling needed
- Use `lib.mkIf` with proper guards instead of conditionals that might fail
- Validate secrets exist before use: `config.age.secrets.secret-name.path`

### Secrets Management (agenix)
- Store secrets in `secrets/` directory with `.age` extension
- Reference secrets using `age.secrets."name"` in configuration
- Always specify `owner` and/or `group` and `mode` for secrets

### Hardware Configuration
- Each host must have a `hardware-configuration.nix` (auto-generated by NixOS installer)
- Copy from the target machine after installation - never reuse from another machine

### Module Design
- Generic modules go in `modules/` directory
- Modules should be host/user-agnostic
- Avoid hardcoding hostnames, usernames, or device paths in modules
- Use NixOS options to make modules configurable

### Home Manager
- User configurations go in `users/<username>/`
- Home Manager configs are imported via `home-manager.users` in host config
- Use `flake-inputs` special arg to access other flakes in HM modules

### State Version
- Always set `home.stateVersion` in Home Manager configs (e.g., "23.11")
- Set `system.stateVersion` in host configs (e.g., "24.11") - do not change once set

## Testing Approach

Since this is infrastructure code, testing is primarily done via:
1. **Dry builds**: `sudo nixos-rebuild dry-build --flake .#hostname`
2. **VM testing**: Test in a VM before applying to real hardware
3. **Eval checking**: `nix eval` the configuration to catch type errors early

No formal test framework is currently set up. Consider adding:
- NixOS tests for critical services
- Custom `tests.nix` in flake outputs for integration testing

## Important Notes

- The `flake.lock` file is auto-generated - commit it
- Use `specialArgs` in `flake.nix` to pass inputs to modules
- The `pkgs-stable` input provides stable nixpkgs for packages that need version stability
- Intel and AMD GPU overlays are defined in `flake.nix` - maintain when adding GPU configs
